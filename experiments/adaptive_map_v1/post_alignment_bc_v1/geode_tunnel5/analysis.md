## 协议与完整性

使用本地 GEODE `gamma2GT_leica.py` 和 `rmse.py`，扫描结束时间、SE(3) 无尺度对齐、
`t_max_diff=0.1 s`，并沿用项目约定在第二个 evo 输入（GT）施加 +0.1 s。该偏移不是
GEODE 官方强制参数。六条轨迹均为 2316 行，覆盖 231.500601 s，最大 CSV 间隔
0.105287 s，无非有限位姿；每次均匹配 623/625 个 GT 时间戳。因此 run02/run03 虽然
发散，也属于完整运行，不能按“提前结束”排除。

所有行均为 `map_diagnostics_v8`；B 的 `adaptive_map=0`，C 的 `adaptive_map=1`。
run01 参数快照确认 blind=2 m、Adaptive Map/invalid-quality 开关符合 B/C 定义，窗口、
后端及其他附加功能关闭。run02/run03 未保存参数快照，六次均未保存 commit、二进制哈希
和启动日志，因此代码/构建来源和每次播放命令不能仅由文件独立恢复。

B/run02 与 B/run03 字节完全相同，且与旧 off_path_alignment_v2 的一个已知稳定分支相同；
初始 C/run02 与 C/run03 字节完全相同。重跑后，当前 C/run02--run04 也字节完全相同，
run05 与初始失败分支哈希相同。用户报告它们是独立运行，本分析不据此认定复制；但从
数值实现角度只观察到稳定和发散两个离散分支，重复文件不能算作不同误差实现。

## 机制解释及边界

观测顺序表明，位姿差在大量 novel 点写入前已经从厘米增长到米级，因此不能断言
“无限 novel 入图是初始发散的唯一原因”。初始失稳更接近弱约束期间的前端分支问题，
当前地图策略没有提供能够恢复位姿的额外约束。

但在位姿偏差变大后，大量扫描点无法找到已有地图邻域，被当前 C 当作可继续生长的 novel
点；由于 Transient novel 配额关闭，这些点被大量放行。这里形成了合理但尚非严格因果证明
的正反馈推断：位姿偏差 -> 邻域丢失 -> novel 大量入图 -> 错误地图继续成为后续参考。
这正暴露了“无邻域等于可信新结构”这一分类假设在严重位姿漂移下不成立。

历史 Tunnel5 的 50 点配额消融发生在成功轨迹分支，单帧 novel 最大仅 20，配额从未触发，
所以不能回答它是否能阻止本次失败分支。当前失败数据首次提供了会大量触发配额的情形。

## 决策

SubT 上 C 表现稳定，但 Tunnel5 显示其最佳精度与最坏稳定性并存。现阶段不能将冻结 C
作为已经通过验证的论文方法，也不应立刻扩大完整 bag 矩阵。

用户选择不启用 50 点上限，重跑确实得到三次新增稳定结果，但 run05 再次精确复现失败
分支。因此“前两次只是一次偶发结果”不成立，冻结 C 仍未通过 Tunnel5 稳定性验证。

CPU/时序敏感性目前是合理假设，但还不是结论：稳定与失败分支消费的 2316 个 LiDAR
起止时间、每帧 IMU 样本数及 IMU 首尾时间完全一致，最大日志间隔也相同，没有输入消息
丢失或 IMU 分组变化的证据。两分支从 frame 1118 的微小位姿/数值差开始分开；当前日志
没有逐帧执行时间、CPU 占用、队列积压或线程调度记录，无法证明 CPU 是原因。

下一步不应继续用同配置无限重跑来挑稳定轨迹。应先做代码级非确定性/数值敏感性检查，
重点核查并发读写、未初始化值、容器/近邻顺序和退化阈值附近的分支；若无明显实现问题，
再设计 0.5x 与 1.0x 的预先固定负载对照并保留系统性能记录。固定配额仍不是当前选择。
